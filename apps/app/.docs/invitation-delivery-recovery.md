# Invitation delivery recovery

The requested increment is safe recovery from interrupted invitation email delivery, shared by Web, CLI and MCP. [[invitation-lifecycle]], [[chat-security]], [[harness-intent]]. It does not decide private administrator visibility or retention, add credentials/resources, send real email, or establish production readiness.

The earlier immediate-send design revoked invitations on any reported error. That conflated definite rejection with acceptance followed by response loss. Keep invitation validity separate from delivery knowledge. A successful create now acknowledges durable intent, not inbox delivery. “Sent” means provider acceptance only; a manager sees that distinction in the UI.

Use the existing invitation row as the minimal outbox: inserting intent and invitation is one atomic write, with no queue service or second store. Existing records migrate to unknown because their historical delivery cannot be reconstructed. Preserve hashes, validity and settled request IDs; never infer that an old invitation was not sent. An additive migration preserves older columns and resource identities. Old binaries do not understand the outbox, so mixed-version sending and production rollback require separate review.

Do not persist a raw link or introduce an encryption credential for replay. Queue intent without a usable secret; issue a new random link and persist only its hash while acquiring a delivery lease. Known rejection can be retried explicitly. After unknown outcome, recovery necessarily invalidates the previous link, including outstanding registration challenges, and submits a new message. The UI requires a specific confirmation, CLI requires an explicit acknowledgement flag, and MCP requires a boolean acknowledgement. Recovery returns current delivery knowledge to CLI/MCP as well as refreshing the UI; an accepted recovery operation must not be mistaken for proof of delivery. A generic create retry never resends. Reusing a stale attempt count cannot send again.

Provisional reversible budgets: at most three dispatch attempts recorded by this dispatcher per invitation (historical sends before migration are unknowable and not counted); ten seconds to observe provider acceptance; sixty-second lease for interrupted workers. No automatic retry, scheduler or unattended delivery promise is introduced. A normal request makes the initial dispatch; after a crash before dispatch, a manager refreshes and resumes queued work. A sending lease remains visible until expiry, then reads show unknown without mutating data. The next authorized recovery fences the expired lease. Timers and workers can stop; elapsed lease time, not a process-local flag, is authoritative.

Current authorization of the operator and inviter, validity, attempt count and delivery state are checked in the same conditional claim. Re-check before calling the adapter to cover revocation or demotion between claiming and dispatch. A database transaction cannot cover the external provider: cancellation after that last check cannot unsend email. It does invalidate the link, and lease-fenced settlement cannot revive a cancelled invitation or overwrite recovery. Old responses after a timeout cannot change unknown into sent. Never treat an exception, ambiguous provider response or worker restart as proof that nothing was delivered.

Void's installed email guide documents stable idempotency keys on Void Platform, but expressly rejects them on the native Cloudflare binding used by this sample. The adapter therefore keeps native keys disabled. It can pass the stable invitation/attempt key only when an integration has explicitly verified provider support; this optional branch is tested with a fake. Different attempts have different links and keys. We cannot replay the original payload after losing the in-memory secret, cannot use a key with changed payload, and do not promise exactly-once delivery on either transport. A delayed previous submission can still yield a duplicate email containing an invalid old link. Do not blindly retry unknown even if a provider supports deduplication.

Recovery operations: refresh the authorized invitation list first. Resume queued or definitely rejected work with the displayed attempt count. For sending, wait for settlement or lease expiry. For unknown, investigate provider metadata through separately authorized operations if available; otherwise explicitly accept possible duplicate email and old-link invalidation before recovery, or cancel. At the bound, cancel and create a distinct invitation only after review. Cancelled and accepted IDs remain closed; inviter restoration does not resurrect cancellation. Expired or currently unauthorized invitations cannot dispatch. No token, lease or provider diagnostic is exposed through management responses, CLI/MCP outputs or application logs. Void's ignored local inbox intentionally captures synthetic mail for development, and is not a public management interface.

Deterministic fake adapters cover timeout, accepted/lost response, fresh dispatcher over persisted intent, duplicate job, explicit failures and bounds, stale recovery, expired leases, cancellation, inviter role loss and late settlement. SQL tests run all checked-in migrations against real SQLite with a transactional D1-shaped adapter; isolated browser/API journeys additionally exercise actual local D1, confirmation/cancellation, old-link rejection and both CLI/MCP recovery. Local Void inbox capture is a fake delivery sink; these tests do not exercise provider deliverability, Cloudflare production retries or physical passkeys. Retention, unattended workers, encrypted replay storage, provider operational lookup and production rollout remain separate decisions.
