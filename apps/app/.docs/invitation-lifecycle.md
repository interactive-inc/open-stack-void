# Invitation and membership authority

The user requested a usable, safe invitation lifecycle and consistent management permissions across clients. Existing passkey registration and transactional single-use consumption are retained; this increment closes stale-authority and duplicate-send gaps. [[chat-security]], [[member-profile]], [[harness-intent]]. Message retention and private-channel administrator visibility remain unconfirmed and are outside this change.

An invitation delegates the inviter's current membership authority, not a permanent right detached from that person. Inferred security policy: require the inviter to remain active and owner/admin both when issuing a challenge and when committing acceptance. A demotion or suspension blocks outstanding invitations; restoring that authority can make an unexpired invitation usable again. Use explicit cancellation for permanent invalidation. Guests always become ordinary members, never a caller-selected role.

Creation is serialized by D1's transactional batch and conditional insert: one unexpired invitation per normalized email, no invitations for registered addresses, and a repeated request ID owned by the same actor/email returns the existing metadata without another email. The browser retains this ID after an uncertain network result. New IDs cannot bypass the pending-email check. The later [[invitation-delivery-recovery]] increment adds explicit bounded recovery with old-link invalidation; creating a distinct invitation still requires cancellation of the pending one. Cancellation is idempotent for a currently authorized manager.

Keep settled request IDs as accepted/revoked records instead of deleting them. Otherwise a delayed create retry can resurrect a cancelled request and send an unexpected email. This finding requires one additive state column; existing rows default to pending. Explicit re-invitation starts a new request ID, while old requests fail closed. Closing also zeros the expiry so older server versions that do not understand state cannot accept those closed links. This is a compatibility precaution, not proof that a production rollback is safe. No database reset or automatic history purge is used.

Historical immediate-send behavior revoked on reported failure and required cancel/reinvite after a crash or lost acknowledgement. This could not distinguish accepted mail from definitive rejection. [[invitation-delivery-recovery]] replaces that policy with durable intent, explicit delivery knowledge and bounded manual recovery. Exactly-once delivery remains unclaimed; no plaintext invitation token is stored for replay or returned through CLI/MCP.

Expired records are retained and shown separately from pending or currently unauthorized invitations; the management view is bounded to the latest 100, with unexpired entries first. No scheduled purge or chat retention policy is introduced. Only the successful invitation action clears its own email draft; other member actions and interrupted requests preserve it. Hide cached invitation rows after a failed permission check or a viewer demotion; error recovery refreshes the viewer as well as lists, because disabling a query alone does not remove its cached data. Compare addresses case-insensitively without rewriting legacy member records.

Membership writes re-check the actor and target roles in the write itself. Status changes update only status, role changes only role; a concurrent promotion cannot be overwritten by a stale disable request. Owners remain immutable, self-mutation through manager operations is denied, and admin status changes target current ordinary members only. Reject checking authority only before persistence: authentication and an earlier read are insufficient for concurrent role changes.

Read invitation metadata and the caller's current authority in one database batch as well. This prevents an earlier authentication result from authorizing a later list snapshot after a concurrent demotion; unauthorized callers receive no invitation rows.

Verification uses synthetic identities in isolated Cloudflare state: expired/cancelled invitations after a challenge, current inviter authority, concurrent acceptance, duplicate creation, idempotent retry, member/anonymous denials and UI recovery after an uncertain response. Count captured messages rather than inbox anchors: Void renders both the subject and a raw-download link for each message. The server remains authoritative even when a displayed invitation status is stale. Real email deliverability and physical passkeys are not established by these local tests.
