# Living documentation contract

`.docs/catalog.json` is the single metadata registry; Markdown is the prose source. Do not duplicate schemas, API inventories or dependency versions in prose. Each owned `.docs/*.md` has a stable ID, status (`proposed`, `current`, `superseded`), kind, evidence (`user`, `observed`, `inferred`), related IDs, implementation/test paths and supersession links. Renames preserve IDs. Historical documents remain readable with explicit supersession; never silently rewrite a rejected choice into a confirmed requirement.

For each material increment record goal/non-goal, domain terms, constraints, assumptions/open questions, rejected alternatives and reasons, compatibility/security consequences, and evidence. Use one concise decision record when one suffices. Link requirements → decision → implementation → verification in the catalog and prose. Mark an AI assumption as inferred until the user confirms it. Unknowns remain unknown; a passing structural check cannot prove semantic truth.

`vp run check:docs` validates registry coverage, IDs, status/evidence, wiki links, supersession, referenced paths and current `vp run` commands. With `DOCS_BASE=<review-base-sha>` it also requires a changed, related decision/requirement record for changes to owned code/tests/tooling. Named exceptions in the catalog are narrow historical command exemptions with reasons, not generic bypasses. Age alone never proves staleness. Review prose against behavior and user intent in every increment, including deliberate no-doc-impact conclusions. Do not update metadata mechanically just to silence a failed gate.

When extracting intent, ask one or two high-impact questions with concrete choices and consequences. Examples: who may see private membership, what a cancellation means, what data retention is required. Record safe reversible assumptions and continue; wait for answers before implementing irreversible policy. Avoid a generic questionnaire. At review, reconcile contradictions and supersede outdated decisions in the same diff.

Before swapping the sample domain, run the acceptance scenario in `scripts/docs-policy.test.mjs`: a nondeveloper's booking request must retain a confirmed requirement, inferred assumption, decision, behavior test and release discipline, without writing a second product. The harness validates structure; an agent/human still judges the chosen business policy and explanatory quality.
