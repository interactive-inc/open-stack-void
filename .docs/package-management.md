# パッケージ管理の選択

利用者の操作を Vite+ に統一し、依存の管理は npm workspaces に変更した。サンプルを試す人がパッケージ管理とタスク実行の書式を使い分けなくて済むことを優先した。[[product-decisions]]。

公開後24時間の待機は維持する。npm の相対的な公開日制限だけでは日時の欠損を拒否できないため、ロック全体を確認する処理を追加した。取得段階では依存スクリプトを無効化し、日時不明や不適格な版を拒否した後に、許可済みのビルドだけを実行する。欠損日時と新しすぎる依存を与え、準備コマンドが依存処理を呼ぶ前に失敗することを分離したテストで確認する。

Windows ではタスク実行中のキャッシュ DB が node_modules 配下で開かれるため、クリーンインストールを vp run の内側で行うと削除と競合する。パッケージ管理コマンドの取得段階と、タスクによる厳格な検証・準備を分けた。グローバル CLI の自己初期化は pnpm 固定の内部環境を作成したため、通常の経路として採用しない。今回その自己初期化が一度実行された範囲はリポジトリ内の無視領域のみで、既存のグローバル設定には触れていない。その後は npm で用意した独立したプロジェクトローカル CLI を使用している。

直接依存の実際の版は移行前に固定し、npm の peer 解決で加わった依存と、監査に基づく修正を区別する。[[dependency-audit]]。通常のデータ、認証、CMS 編集内容は依存ツリーと分離して保持する。

npm の hoist では React プラグインからアプリ配下のコンパイラーを参照できなかったため、既に使用していたコンパイラーをルートにも明示した。Astro の古い optional peer と実際の React プラグインの要求が食い違うため、同じ使用済みの版へ限定して整合させた。peer 全体の検査や engine 判定は無効化しない。

空の端末に CLI を用意する最初の一手は別の前提条件である。公式のプロジェクトローカル CLI は Node と既存パッケージ管理を必要とするため、グローバル初期化を使わず完全にゼロから vp だけで導入できたとは主張しない。検証対象は npm で用意した独立 CLI と、そこからのプロジェクトの新規インストール・準備・開発操作である。

その後、公開 provenance が指す1.4.0のソースで、Windows の標準初期化が pnpm を固定して実行することを確認した。初期化は再実行せず、クリーン導入の制約として区別した。[[clean-bootstrap]]。

後続のユーザー確認で、利用者の操作入口が VP であれば公式インストーラー内部の処理は許容することになった。上記は当時の調査履歴として保持し、現在の判断は [[harness-intent]] を正とする。プロジェクトの npm バックエンドと24時間制限は維持する。
