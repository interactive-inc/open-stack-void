# 公開先の構成

紹介サイトは `stack.open.inta.site`、同梱の会話アプリは `app.stack.open.inta.site` に分ける。製品開発本部のアカウントを使う。

最初に旧構成を公開した際の会話アプリの保存先は、既に割り当てられた識別子とデータを維持するため `open-stack-void-db` を引き継ぐ。公開サイトの保存先と混在させない。[[resource-naming]]。

公開サイトは、管理者が未登録のまま匿名の訪問者に所有されることを防ぐため、初回設定用の経路を `EMDASH_SETUP_LOCKED` で閉じる。管理者本人の登録時だけ保護された方法で開く。会話アプリの初回所有者も、専用の初期化キーを設定するまで登録できない。所有者の登録と実メールの設定は、サイトの公開とは別に行う。

初回設定の操作は、Workerのシークレットとして保存した `EMDASH_SETUP_KEY` と一致する要求だけを受け付ける。公開コンテンツの投入はこの経路で行い、管理者や認証情報は作成しない。

会話アプリの初回登録用の連絡先は `takata@inta.co.jp`。初回登録の鍵を本番へ設定し、登録画面が表示されるところまで確認した。端末内の鍵は `.local/app-production-setup-key` に保存する。記事管理用の鍵とは別に扱う。本人が端末の認証器で登録を完了するまで、管理者や認証情報は作成しない。

通常の初期設定画面は専用の要求ヘッダーを送れないため、初期設定の鍵を入力する入口を設ける。鍵はアドレスに含めず、送信後は保護された短時間の閲覧情報で同じブラウザからの操作を許可する。管理者本人が生体認証や端末の認証器を操作して登録を完了する。端末内の鍵は `.local/site-production-setup-key` に保存する。

会話アプリの公開前検査は、分離した一時領域へ生成済みの設定を複写しないため、既存の型設定を明示する必要がある。依存の内部にだけ置かれていた保存処理の部品も、検査道具が参照できるようルートへ同じ版で明示した。公開前の検査を省略する意図はない。

```sh
TSX_TSCONFIG_PATH="$PWD/apps/app/tsconfig.json" vp -C apps/app exec void deploy
PUBLIC_APP_URL=https://app.stack.open.inta.site PORTLESS_URL=https://stack.open.inta.site vp -C apps/site run deploy
```

この記録は過去の公開作業で観測した構成と、ユーザーが選んだ公開先を引き継ぐ。今回の統合では公開設定と資源の識別子、初期設定保護を復元するだけで、本番の所有者登録状態・配信設定・稼働確認を更新したとは扱わない。ローカルでは初期内容投入を妨げないよう、本番の保護を開発実行時に適用しない。既存の保護を削除する案は未設定サイトの所有者登録を露出するため採用しない。[[chat-usability]] と [[user-guide]] の検証と本番反映は区別する。

初期設定保護の単体試験で、鍵が未設定または不一致なら拒否すること、外部Originから解錠できないこと、短時間のSecure/HttpOnly/SameSite属性と公開ページの通常閲覧を確認する。本番の実行結果と見なさない。

2026-10-27、ユーザーの依頼で紹介サイトと会話アプリを検索インデックスの対象外とする。公開HTMLにはnoindexのメタ情報を付け、アプリのページとAPI、サイトのWorker応答と静的アセットにも対応する応答ヘッダーを付ける。クロール自体は妨げず、検索側が除外指定を読めるようにする。これはアクセス制御の代替ではなく、既存の認証・初期設定保護は維持する。ソースのmainへのプッシュと、本番の反映・検索側の処理完了は分けて報告する。検証はローカルHTTP・HTMLとビルド生成物で行う。

このnoindex追加は整形・lint・構造・文書・単体・型・全体ビルドを通過し、アプリのブラウザ試験3件でHTMLのメタ情報とページ・APIの応答ヘッダーを確認した。CMS試験1件ではサイトのメタ情報と既存の編集・公開・リンク動作を確認し、サイトのビルド生成物にも静的配信ヘッダーとWorkerの設定が残ることを確認した。公開済みドメインでの応答と検索エンジン側の削除完了は検証していない。

## Release branch and publication

2026-10-28、ユーザーは公開用に `release` ブランチを1つ使う方針を選んだ。通常の開発は `main`、公開する変更はプルリクエストで `release` に取り込む。`release` は管理者にも適用する保護を設け、最新の `verify` 必須チェックとプルリクエストを要求し、強制プッシュと削除を許可しない。単独運用のため別の人の承認人数は要求しない。レビューで変更と検証結果を確認してから取り込む。

GitHubの検証は `main` と `release` へのpush、およびプルリクエストで実行する。公開は明示的な依頼を受け、クリーンな `release` のチェックアウトで `vp run deploy:production` を実行する。このコマンドは公開先ブランチの保護・リモートSHA・同一SHAのrelease pushのCI成功と実行証跡を確認し、端末で秘密情報検査を実行してから、既存のCloudflare認証でアプリとサイトを公開する。CIでは全E2Eを含む検証を実行し、3つのブラウザ試験群・完全検証・クリーンなコミット・同一SHAの秘密情報検査を明示的な追加ステップで確認する。複数アカウントがある端末でも既存の公開先アカウントを明示して選択する。GitHubへCloudflareの秘密情報を追加せず、自動公開は行わない。必要な依存関係、ブラウザと検査道具は通常のセットアップ手順で準備する。[[core-verification]]、[[core-delivery]]。

アプリとサイトは順に公開されるため、片方だけ成功する可能性がある。失敗時は実際の公開バージョンとデータ互換性を調べ、成功した部分も含めて報告する。コマンドはDBを復元しない。移行がある場合は公開前に内容・互換性・回復手順を確認する。以前の直接公開コマンドは過去の手順として残し、通常の公開入口はこの検証付きコマンドとする。設定の存在と実際のGitHub保護・本番応答は別々に確認する。

公開経路の検証中、ブラウザの初期化より先にエラー表示の確認を始める競合、別領域に同時に出た警告を区別しない招待試験、CMS操作と全リンク巡回が1つの時間枠を共有する問題を観測した。初期化試験は合成した503応答を待ってから同じエラー表示・操作禁止・復旧を確認する。招待試験はメンバーダイアログ内の警告と再読み込みを対象にする。CMSは操作・公開と全リンク巡回を直列の別試験に分け、各試験の制限時間、全リンク、HTTP状態、ガイド到達性の期待値を維持する。ローカルD1の一時的な内部エラーそのものを修正したとは扱わない。公開前の全試験と秘密情報検査は引き続き必須とする。

公開直前の再確認では、ブランチ名・クリーン状態・リモートSHAに加え、端末のHEADも検証開始時のSHAと一致することを要求する。検証後に別のコミットへ移動した場合は、同じブランチ名でも公開しない。

公開前の全検証は、ポートやローカルデータを共有しないGitHubの専用環境を正本とする。端末で通常開発用のポートを使うブラウザ試験を繰り返す方式は、別プロジェクトの開発サーバーと衝突したため採用しない。公開コマンドはreleaseへのpushで実行された所定のワークフローだけを認め、全検証・秘密情報検査・クリーンな同一コミットの確認の各ステップが成功していなければ停止する。mainやPRの成功だけ、部分検証、ステップ省略、別SHAや変更済み作業領域の証跡では公開しない。端末のローカル検証は開発中の確認に使い、他のアプリを停止して公開条件を整える運用にはしない。
